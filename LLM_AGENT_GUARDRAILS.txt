ATK LLM AGENT GUARDRAILS
Repository-wide inventory
Reviewed: 2026-11-24

PURPOSE AND SCOPE

This report inventories guardrails visible in the ATK repository's LLM-backed
agents, their frontend flows, gateway controls, and deployment configuration.
It distinguishes prompt instructions and configurable controls from safeguards
whose runtime enforcement is evident in code. The principal code areas reviewed
are ITOpsToolkit_Backend, ITOpsToolkit_Frontend, ITOpsToolkit_Agent_Gateway,
ITOpsToolkit_Build, and the LiteLLM/Bedrock deployment configuration.

KEY FINDINGS

1. Most backend modules declare an LLM guard called "Bias", but their scanner
   registries use lowercase names and match names case-sensitively. As a result,
   those module declarations select no scanners. Problem Assist uses lowercase
   names and is the clear exception.
2. Even where scanners run, the inspected flows generally continue with the
   scanner's transformed text and do not reject content based on its validity
   or risk result. Malicious-URL scanning is commented out in the reviewed
   backend implementations.
3. Most agent safeguards are prompt instructions (grounding, output format,
   task scope), rather than hard validation or authorization boundaries.
4. MCP tool selection limits which tools an agent is offered, but the
   ServiceNow MCP server's per-tool RBAC checks are commented out. A separate
   RBAC file exists but is not applied in that server path.
5. Bedrock Guardrail resources are configured in Terraform, but the reviewed
   code does not establish that agent calls attach/use them. LiteLLM deployment
   configurations reviewed do not declare content guardrails.
6. Gateway authentication, authorization, and external guardrail processors
   are configurable capabilities; the repository does not establish that
   policies are active for the product agents. The gateway engine is a
   container image, not inspected implementation source.

BACKEND AGENTS BY MODULE

Shared runtime pattern

- Module prompt libraries generally configure model "azure_gpt4o" and the
  "demo_eks_instance" ITSM tag. These are routing/context settings, not safety
  enforcement. Example:
  ITOpsToolkit_Backend/modules/change_assist/config/system_prompts.yaml:1-7
- Scanner implementations include input toxicity, gibberish, banned-code,
  prompt-injection, and PII anonymization checks; output scanning includes
  toxicity, gibberish, banned-code, deanonymization, and bias. The cited
  Knowledge Assist registry illustrates the available scanner maps:
  ITOpsToolkit_Backend/modules/knowledge_assist/utils/knowledge_assist_agent.py:191-218
- Scanner thresholds shown in the implementation are 0.5 for toxicity and
  prompt-injection checks. Malicious-URL checks are commented out; Secrets is
  imported but not included in the scanner maps.
- Change, Incident, Knowledge, Meeting, MIM, and Train configuration files
  declare "Bias", whereas scanner registry keys are lowercase and selection
  uses a case-sensitive membership check. Consequently, these declarations
  yield empty input and output scanner lists. Example implementation:
  ITOpsToolkit_Backend/modules/change_assist/utils/change_assist_agent.py:418-444
- Scanner calls do not consistently gate execution on scanner validity/risk
  flags. The shared missing-prompt fallback also has an unsafe None path:
  ITOpsToolkit_Backend/modules/change_assist/utils/system_config_ca.py:68-91
  (the pattern is repeated in module system-config helpers).

Change Assist

- Agent types include prompt refactoring, architecture-image analysis,
  topology insights, and change creation.
- Prompts constrain output shape and intent: refined prompt only, raw topology
  tool output, and JSON change plans with impact analysis grounded in the
  available context.
- MCP and image-analysis tools are exposed to selected agents, but the
  module's configured "Bias" scanner does not match the lowercase scanner map.
- ChangeRequest Pydantic models exist, but the main generated response is not
  validated against them in the noted flow.

Problem Assist

- Approval-related fields exist, but the path that creates a problem ticket
  does not check approval status before calling the create operation.
- Reactive retrieval uses a configurable k (default 4) and similarity
  threshold 0.1.

Other backend modules and cross-cutting controls

- No additional LLM agent behavior was identified in the Administration/Auth
  modules during this inventory; their absence should not be read as a
  guarantee that no indirect LLM integration exists.
- ServiceNow MCP has token introspection, but loading RBAC and checking
  per-tool permissions are commented out. The separate mcp_rbac.yaml lists
  basic/privileged groups but is not applied by the reviewed server code.
- The shared LiteLLM client permits max_tokens=None by default. Usage tracking
  is present, but is not a request rate limit. No per-agent rate limit or

FRONTEND AGENT FLOWS

FASTE SOP agent

- The frontend sends user text and current SOP content to the SOP service;
  it does not define the agent's system prompt, enabled tools, or execution
  policy. Quick-start prompts mention MCP but do not establish which tools
  the backend enables.
- Document upload has a 10 MB limit and accepts PDF/Word types/extensions.
  These client checks do not prove server-side validation or instruction
  sanitization of extracted content.
- SOP submission checks required headings and nonempty content. The pre-check
  flag is set immediately when clicked rather than waiting for a successful
  agent pre-check response. Submission stores is_approved as False, so the
  SOP is queued as unapproved rather than auto-approved.

AGENT GATEWAY

- The configuration schema supports CEL allow/deny/require authorization rules
  over MCP tools, prompts, and resources, plus local MCP authentication with
  issuer, audience, and JWKS settings. The UI defaults auth mode to strict and
  checks issuer/JWKS fields when saving. These are capabilities; no active
  product-agent policy was established.
- External MCP guardrail processors can match methods and request/response
  phases. failClosed is the schema default, but the editor permits failOpen.
  Unmatched methods bypass a processor. The gateway routes to an external
  policy service; the schema does not implement content-safety logic itself.
- Config validation uses AJV against JSON schema. The authorization editor
  checks nonempty/duplicate CEL expressions but not their policy semantics.
- MCP Playground can call discovered tools. Raw arguments must parse as a JSON
  object, but are not validated there against the full tool input schema; the
  bearer-token field is optional.
- LLM Playground allows editable system prompts and user-supplied tools; tools
  are sent with tool_choice=auto. No prompt moderation or tool allowlist was
  evident in that path.
- The engine Dockerfile references an external container image; repository
  source does not establish engine-side enforcement.

DEPLOYMENT AND INFRASTRUCTURE

- AWS Bedrock Terraform defines a content guardrail with high input/output
  filtering for hate, insults, sexual content, violence, and misconduct.
  Prompt-attack filtering is high on input and NONE on output. It anonymizes
  email, phone, and name and blocks US SSNs and payment-card numbers. This is
  configured guardrail infrastructure; attachment to agent requests was not
  established.
- The reviewed IAM policy permits invocation across foundation-model/* and
  provisioned-model/* and allows ApplyGuardrail for guardrail resources; no
  model allowlist is evident in that policy.
- LiteLLM Docker Compose/AKS/EKS config reviewed contains database settings,
  not model/content guardrail definitions. Deployment credentials and Nginx
  routing are access/routing controls, not agent content-safety rules.
- Build deployment bundles also contain copied prompt YAML with guard lists.
  These are declarations and may vary by bundle/package (some list Bias only,
  others broader guard names such as PromptInjection, Toxicity, MaliciousURLs,
  Anonymization, and Bias). Verify the deployed package/version; declaration
  alone does not demonstrate runtime enforcement.

RECOMMENDED PRIORITIES

1. Correct guard-name normalization/mapping and add tests asserting which
   scanners are actually active for every module and deployment bundle.
2. Make scanner results an explicit decision point: reject, redact, or require
   review according to defined policy instead of ignoring validity/risk flags.
3. Enforce tool-level authorization in the MCP server and verify each agent's
   effective tool set against least-privilege requirements.
4. Validate LLM outputs against schemas at the backend boundary before using
   them for ITSM writes; enforce approval on the server for actions that
   require human review.
5. Test/verify that configured Bedrock or external gateway guardrails are
   attached and fail closed on every intended request path; document which
   policies are active per environment.
6. Fix the SOP pre-check flow so submission depends on a completed successful
   check, and validate uploaded content on the server as well as in the UI.

LIMITATIONS

This is a repository-code/configuration inventory, not a penetration test or
runtime deployment verification. References show where relevant behavior or
configuration was observed. "Not evident" means it was not established in the
reviewed paths and should be confirmed against deployed services and runtime
configuration.
